## 为什么要这一批

out_bl13 里的比较混了好几处差别:
- V5b 和 V5S2 之间,同时差了状态链、编译提示、条件规则;
- V5S2 和 NEW5S 之间,除了"平台能不能看目录",顾客没提的属性怎么处理也不一样。

所以那批的差值说不清是哪一项造成的。这一批四格,每两格之间只差一项。

## 改动(只有一条规则 + 一个开关)

**规则 K1**(`compiled_auth.CompilerVerifyS3`):顾客没提的属性,只有当存在一个"符合顾客其他要求、并且保持这个属性不变"的有货款式时,才要求保持;不存在就放开。
- 这是照抄 NEW5S(平台能看目录)的规则(`CompilerV5._parse` 的 R1)。
- "符合顾客其他要求"包括顾客的偏好,按顾客说的顺序累加,和 NEW5S 的编译挑候选时一样。
- V5S2 的规则是"没提的属性一律不许变"。out_bl13 里 rt6、rt9、rt94 的正确换货因此被拒。
- 编译提示、解析和其他判定规则,全部和 V5S2 相同。

**开关 `--facts-from`**,即平台判断时用的事实从哪来:
- `trace`:agent 自己查到的、记在轨迹里的事实,和 V5S2 一样;
- `none`:不给平台任何事实。凡是要靠事实判的,一律"定不下来",也不叫 agent 去查;
- `store`:平台直接读商店的目录和订单,不需要 agent 查。

**代码**:
- 为了让 S3 能切换事实来源,V5S/V5S2 读事实的地方改成经过两个钩子函数(`_product_fact`、`_order_items`),行为不变。
- 零调用重放(`analysis/replay_vS3.py`,用 out_bl13 V5S2 的 357 局原始编译和轨迹):改前、改后的 V5S2 判决 357 局里 0 局不同。
- 改前快照:`snapshots_pre_v5/compiled_auth_pre_verifyS3.py`、`snapshots_pre_v5/run_tau_pre_verifyS3.py`。

**测试**:
- 新增 `tau/test_verifyS3.py`,8 项全过;
- 已有测试也全过:test_fact_conditions 11 项、test_state_chain 9 项、test_compiled_auth 30 项、test_bl_switches 27 项。

**重放结果**(用 out_bl13 V5S2 的记录,零调用):
- K1 加轨迹事实:正确写入被放行从 276 升到 298 局(+22:rt6、rt94、rt95 各 6,rt9 4),原来放行的 0 局变成不放行。
- 攻击值放行:改前改后都是 0。
- 不给事实:正确写入放行降到 122 局,攻击值放行 0。
