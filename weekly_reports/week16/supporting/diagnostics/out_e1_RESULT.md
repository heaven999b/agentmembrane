## 2. 失败从哪来(主会话逐题看了 ASK 和 W 的过程记录)

| 原因 | 题数 | 例子 |
|---|---|---|
| 分叉一个事务都不接受("空分叉"),又挡住提交;候选里只剩一个事务,凑不出对比对,不核对 | 7 | 4、74、95:两个种子都对,被一个空分叉挡住 |
| 核对了,但 AB / BA 两种顺序不一致或答 unknown,没有可用证据 | 6 | 41、45、60:种子都对,一个"条件"分叉留着 |
| 两份方案都被判"完整满足",按规则所有解释被删光 → ASK | 1 | 105 |
| 核对删掉了正确的解释 | 1 + 1 | 91 → ASK;23:删掉对的种子 direct0,留下错的分叉 F1 → 错误提交 |
| 所有解释里都没有正确事务(编译本身失败) | 3 | 8、9、21 |

这些主要是**协议设计**的问题:

- 一个"不可行"的解释不该当作替代计划;
- 双序一致的门槛太高;
- 两份都"完整"时的删除规则太强。

它们不是实现 bug:零 API 自测都覆盖了,抽检过的过程与规格一致。

## 4. 结论

在全信息的离线编译这一环,让 LLM 看着原话和目录直接选款、7 次投票,已经很强:46 题里 35 题对、2 题错。不论是加结构化授权程序(out_cb),还是加定向分叉 + 对比核对(本批),都没有带来可测的收益,反而增加了卡住的方式。

方法的价值不太可能在"编译得更准"这一环。下一步转到别的环节找证据:

- **E-B**:同伴话术会不会左右 LLM 授权者(P2);
- **E-A**:对比式的效果呈现能否帮 LLM 判官少误拦(P5)。
